# ADR 012 — one application environment and bounded real scenarios

Supersedes ADR 011's dedicated runtime requirement. Keep app/PostgreSQL/RabbitMQ/frontend separation in the existing Compose project. Compose demo routes into main HTTP; Supervisor still owns HTTP, relay and consumer. Main database backup, verified disposable restore, existing checksums and forward-only migration are prerequisites for adoption. Export legacy evidence and stop only ownership-verified legacy containers; retain their volumes. Never reset original evidence or rotate existing infrastructure credentials implicitly.

Four fixed producer intents: normal, dedupe, concurrent, recovery; each starts unique stock 10 with a business fact + canonical outbox event for quantity 5 in one commit. Request identity survives reload/uncertainty. One duplicate action per run, copies=1 (dedupe) or 3 (concurrent); unique run and request constraints, identical retry returns the same action, divergent reuse conflicts. Action admission requires the original receipt and relay completion. Original outbox and business history are never reset. Background action worker is single-flight and independent of browser cancellation. Queued actions resume after restart; executing actions become unknown and are never automatically republished. Each action has a 20-second execution deadline and at most three publication calls. Publication uncertainty cannot promise exactly two/four arrivals.

A duplicate action uses the existing broker/vhost/direct exchange and a durable bounded queue/routing key `relay.demo.<action UUID>`, preserving the original envelope/message_id. One or two temporary consumer sessions (prefetch 1) exercise the existing delivery handler and atomic inventory repository; no extra permanent process or increased production consumer prefetch. Concurrent sessions meet a barrier before processing their first deliveries. Queue-specific routing prevents these temporary contexts consuming unrelated work. Retain queue/observation evidence; no purge. At most 100 runs/queues, one action/run, two action contexts globally, pool 2 dedicated to the action worker. Temporary sessions always close on deadline/shutdown; remaining deliveries stay in the owned durable queue for inspection, not silent retry.

For demo-owned events only, Applied and Duplicate observations commit in the consumer transaction (Duplicate commits its classification record, with no stock mutation). Serialize the observation cap under the run row: at most 32/run, then records are a lower bound and expose saturation. Optional publisher observations are bounded to 32/run and must not change successful delivery semantics if their storage fails. Observed_at is local/database observation time, not an exact broker timestamp. Receipt remains the business-effect proof; ACK-send return remains distinct from broker receipt.

Recovery uses one durable run-scoped rejection before AMQP send, not infrastructure failure or a fabricated broker NACK. Generic `RejectedBeforeSend` is explicitly scheduled through existing retry ownership/policy with before_send evidence. A durable fault row is consumed once; retry schedule/revision are retained there in the same transaction as the actual relay schedule, preserving proof after eventual success. Event identity and original outbox history remain. If failure injection commit acknowledgement is lost, no broker call occurs in that attempt; the outcome is uncertain until durable inspection/recovery. Normal finite relay retry/lease budgets apply.

One local demo principal via separate bearer token and exact browser Origin; no cookies/CORS/browser secret bundle/admin shell/SQL/Docker endpoint. Existing rate/body/pool/run caps remain. Browser polls sequentially every second for 60 seconds, displays independent evidence and preserves request/action IDs across unknown responses. Closing stops observation only. No process-local counter is durable run proof. Old crash/race/ACK-loss playback remains clearly Illustrative. No public-production or exactly-once transport guarantee.

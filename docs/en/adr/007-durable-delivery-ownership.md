# ADR 007 — Durable delivery ownership with short transactions

Accepted — 2026-10-09, Milestone 2.2. Decision recorded before implementation. Verified baseline: clean `5eac9ff`; ADRs 001–006, existing reader and publisher inspected.

Hold a row lock and transaction during publication: this serializes database owners but retains a connection and locks throughout network waits, complicates cancellation, and still duplicates when broker acceptance precedes rollback or lost COMMIT acknowledgement. Crashes release locks but cannot undo publication. This is unsuitable for the bounded publisher's remote waits.

Choose a durable lease acquired atomically in a short transaction, publish outside the transaction, then complete or release in another short transaction. Each acquisition gets a fresh non-nil UUID ownership token distinct from the event ID. No separate processing status: leased rows remain pending, and expiry restores eligibility without a reaper update. This preserves reader semantics and avoids retaining connections during external I/O. Costs are additional metadata, clock discipline, stale-owner predicates and possible overlapping external publication after expiry. CDC, distributed transactions and advisory-lock-only ownership add machinery or lack durable expiry without satisfying a demonstrated requirement.

An event snapshot is data, never transition authority. Event identity remains unchanged across acquisitions and publication. A token protects database transitions only: RabbitMQ does not fence it. Expired/cancelled workers may still publish; acceptance followed by failed or uncertain completion may duplicate during recovery. Exactly-once and end-to-end at-least-once delivery are not established.

## Lifecycle and authority

States remain pending, processed, dead_letter. Terminal states have no lease; processed alone has processed_at. No terminal escape or dead-letter transition API is introduced. A pending row is acquirable when available_at <= database time, its lease is absent or expires_at <= database time, and its attempt count is below 2147483647. Acquisition replaces expired ownership atomically, increments the count once, and writes token/acquired_at/expires_at together. Ownership starts at committed acquisition, ends at expiry or committed completion/release. Return owned data only after known commit success. A slow acquisition may return an already expired lease; callers must not interpret returned data as perpetually valid.

Use a database clock_timestamp() sample taken after row-lock acquisition for each transition; use that one instant for predicates and stored timestamps. Do not use caller wall time or transaction-start now() after lock waits. Expiration is inclusive: at expires_at ownership is lost. Completion/release require matching event ID and token, pending status, acquired_at <= sampled time < expires_at. Even before reacquisition an expired owner is rejected. Clock reversal before acquired_at rejects mutation; no monotonic-clock guarantee is claimed. Milestone 2.3 must test SQL predicate evaluation after lock waits.

Lease duration is positive whole microseconds within signed i64 microseconds; addition must be checked. Lease timestamps use microsecond precision and expires_at > acquired_at. Available_at retains earliest scheduling eligibility and is unchanged by acquire/release; release simply clears ownership, leaving pending immediately eligible if availability is due. No backoff, retry schedule, error-storage or quarantine API is selected. Processed_at is the database completion instant after confirmed broker acceptance, never consumer processing time. Completion clears ownership atomically. Rejected, unroutable, unavailable, serialization failure and uncertain publication do not authorize completion; future use cases enforce that ordering.

Attempt_count counts committed acquisitions, including recovery acquisitions whose workers crash before publishing. It does not count actual sends. Existing nonzero counts are retained as historical metadata; exact pre-milestone occurrences cannot be reconstructed. INTEGER remains bounded at 2147483647; never wrap/saturate. Exhausted rows remain observable pending but cannot be acquired; remediation policy is deferred. Model acquisition reports AttemptLimit; persistence acquisition excludes exhausted candidates and empty success does not imply an empty backlog.

No match is OwnershipLost, distinct from infrastructure errors. Repeated completion/release is rejected, including after a successful earlier call; it is not idempotent success. Matching terminal identity alone is insufficient evidence of this owner's success. Mutation errors are sanitized PersistenceError values; CommitUncertain means the transaction may have committed. Known failure must not be used for unknown commit outcome. On uncertain acquisition do not publish from an unconfirmed claim; let expiry recover it. On uncertain completion/release do not assume either success or retained authority; reconcile durable state operationally or allow lease recovery. Cancellation after dispatch may have the same unknown outcome even without an error return. Do not blindly repeat acquisition with its old token, nor regenerate event identity.

## Schema and implementation boundary

Add nullable ownership_token, acquired_at and expires_at in a new migration. All three absent or all present, non-nil token, finite timestamps, pending status, positive attempts, expiration after acquisition and available_at <= acquired_at. Existing rows retain every envelope/metadata value and start unowned. Keep the pending availability index: planned acquisition scans due candidates in available_at/created_at/id order, filters lease expiry and attempt limit, and locks with SKIP LOCKED in 2.3. No time-dependent partial index or speculative extra index; measure leased-row scan cost later. Existing SELECT columns/predicates remain compatible and may observe leased pending rows. Constraints enforce row shape, not transition history or token freshness across all history.

2.2 provides models, separate acquisition/completion/release Send-future static contracts, migration and tests only. Models own invariants; repositories own SQL; use cases own orchestration; adapters own publication. 2.3 implements PostgreSQL operations and real locking/concurrent mutation/commit uncertainty integration tests. 2.4 implements claim/publish/persist, 2.5 worker/composition/reconnection/Supervisor, 2.6 end-to-end crash/recovery. Fakes and pure transitions prove no PostgreSQL concurrency guarantee.

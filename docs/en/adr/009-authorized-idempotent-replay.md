# ADR 009 — Authorized, idempotent and auditable replay

Accepted — 2026-10-13, Milestone 3.5. Baseline Rust `3df5942f1dfb944fc294dcbc0d27d2f0daeedd16`; Engineering Library `fd61b2123aa7a6b59679c603f70bbd7d459c5c2a`. Both were clean. ADRs 007/008, 3.1–3.4, current ownership/retry/discovery, migrations, HTTP, worker and isolated fault harnesses informed this decision.

## Trust boundary

Choose an opt-in focused HTTP bearer API rather than an OS/database CLI identity or a full identity platform. Trusted deployment configuration maps a random 256-bit hex credential to a stable actor, `allow_replay` permission and maximum budget (1–100). No actor/admin assertion is accepted in request JSON. Default empty/unset configuration disables privileged routes. Authenticated observers with permission false cannot replay, repeat or query. Scope is global `outbox:replay`: there is no tenant model. Operators may replay any eligible event but can only inspect receipts attributed to their own actor and scope. This is a local administrative capability; protect configuration, restrict network access, use distinct credentials per actor and revoke by removing credentials and explicitly redeploying. It is not a complete identity/rotation platform.

Authorization precedes storage on every use-case path, including repeated submissions and lookup. Outcome queries filter actor/scope in SQL. Guessed request IDs do not disclose another actor's receipt. A collision with an existing foreign request gets generic intent conflict, without exposing intent or audit content. Pure models and native Send-future ports are independent of SQLx/HTTP; the transport authenticates, application validates/authorizes, infrastructure owns SQL/locking. No frontend login or replay button.

## Contract and eligibility

POST `/operator/replays` supplies a non-nil request/event UUID, expected nonnegative revision and positive cycle, required printable ASCII reason (1–256 bytes, nonblank), positive budget (1–100 and within the actor's configured ceiling), delay 0–86400000 ms and optional non-nil ticket UUID. Unknown fields are rejected; HTTP JSON body is bounded at 4096 bytes. Canonical association is explicit JSON fields plus actor/scope, stored as JSONB and compared structurally. Strings compare exactly; omitted/null ticket means the same absent optional value. Request uniqueness is global UUID, not per event or actor.

Eligible preserved dead_letter reasons: legacy_dead_letter, serialization_permanent, invalid_stored_envelope, acquisition_budget_exhausted, storage_counter_exhausted, subject to current validation. Reject missing/pending/processed/stale rows. Restore the envelope using the current checked reader/acquirer contract, validate supported timestamps/JSONB, coherent cycle/baseline/count, absent entire ownership tuple and processed_at, terminal/diagnostic evidence and reason consistency. Positive u32 schema versions are envelope metadata, not a business payload catalog. Unsupported representations or invalid content reject without mutation. A previously isolated invalid event only becomes replayable if separately authorized repair or a supported interpretation change permits restoration; replay itself performs no repair. Unsafe identity/history/ownership requires separate audited repair.

Cycle increments once, baseline becomes current lifetime count, selected budget is stored, availability uses post-lock PostgreSQL clock_timestamp plus the selected delay. Revision increments safely. Preserve ID, event/creation timestamps, schema version, aggregate/correlation/causation metadata and exact stored JSONB; never rewrite the envelope. Preserve lifetime attempt_count. No ownership token is reused or minted by replay; normal subsequent acquisition supplies a fresh token. Clear terminal/diagnostic/legacy error fields for pending state after retaining their prior values in the restricted audit.

Lifetime i32::MAX cannot represent another acquisition and is rejected; cycle i32::MAX is rejected. Require room for replay plus at least one acquisition and completion (revision <= i64::MAX−3). A budget is an upper allowance, not a guarantee all acquisitions can fit remaining numeric capacity; ordinary acquisition still checks storage capacity. Widening counters requires a separate policy/migration; no reset/wrap/saturation.

## Atomicity, locking and outcomes

Use the existing short Read Committed transaction and commit-error classification. Lock order: pg_advisory_xact_lock(hashtextextended(request UUID text,3500)), read durable request, then SELECT exact event FOR UPDATE. Hash collisions only serialize unrelated requests; the table UUID primary key enforces uniqueness. Each operation takes one request lock and one event lock; ownership/discovery/maintenance never acquire replay request locks. Do not reverse that order or add multi-event batches. No broker I/O or hidden transaction retry loops.

After any lock wait recheck the current committed row and sample clock in a separate statement after event lock. Identical actor/scope/intent returns its previously committed receipt regardless of current event state, without opening another cycle. Changed association returns IntentConflict. Different request UUIDs for the same expected revision serialize at the event and only one succeeds. Discovery/maintenance revalidate their own pending predicates; they cannot use a stale terminal snapshot to mutate a replayed event. Workers may acquire immediately after replay commit, even before the HTTP result arrives.

New migration `20261013000000` inserts receipt, explicit intent, actor/reason and prior terminal evidence atomically with the cycle transition. `decided_at` is post-lock decision time, not a measurement of the exact commit instant; receipt is returned only after acknowledged commit. Prior evidence contains reason/time, diagnostics, evidence, legacy error, predecessor cycle/baseline/budget/revision and lifetime count. HTTP returns only the receipt, never original payload, free-form reason or prior evidence. The application has no audit UPDATE/DELETE path; a trigger also rejects UPDATE/DELETE/TRUNCATE. Revoke PUBLIC access; production roles need only SELECT/INSERT on audit plus required event privileges. Current local database owner can disable triggers/drop objects; this is application-immutable audit, not tamper-proof storage. No automatic retention/deletion.

Rejected requests do not receive transactional audit rows; they have sanitized operational diagnostics. Failures before authentication/transaction cannot be claimed as durable audit. Ordinary server rejection rolls back both writes, including deferred COMMIT rejection. Lost acknowledgement is CommitUncertain. Cancellation may suppress a committed result; SQLx 0.8.6 Drop queues rollback and does not prove immediate rollback or undo committed work. GET `/operator/replays/{request_id}` is authenticated read-only observation. Negative lookup is only current visibility, not proof an in-flight transaction will never commit. Repeating the exact same authorized request safely coordinates on the request lock and returns its receipt; never generate a new request UUID automatically after uncertainty.

A receipt means work was re-enabled, not RabbitMQ acceptance or consumer business effect. Replay does not immediately publish, undo past effects or guarantee another effect; consumer idempotency remains independent.

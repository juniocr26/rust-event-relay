# ADR 011: persistent local successful-delivery runs

Accepted for Milestone 6.1. One dedicated reusable Compose project `relay-demo61`, separate PostgreSQL and RabbitMQ volumes, no Docker socket in applications. Existing shared services are outside the mutation boundary.

`POST /demo/runs` takes a UUID request_id and fixed intent: scenario=normal, initial_stock=10, quantity=5. A durable UUID run/event/fact and unique warehouse/SKU are created together with fixture stock 10 and canonical outbox INSERT in one PostgreSQL transaction. The producer does not apply the receipt effect. A database advisory transaction lock serializes admission and request reconciliation; unique constraints protect identity. Same identity/intent returns the same committed run; changed intent conflicts, including unsupported changed values. Failed statements roll back. COMMIT acknowledgement loss is unknown: recover by GET using request_id or repeat exactly the same submission. Never generate a replacement identity automatically.

202 means producer commit acknowledged, not delivery. Evidence independently reports outbox status/processed_at, consumer receipt and current stock. A completed receipt proves its local stock effect committed. Relay processed proves relay completion after publisher confirmation, not consumer completion or an exact broker timestamp. No observed lease/confirm/ACK history is invented. One read statement supplies a PostgreSQL statement snapshot; no distributed broker snapshot exists. Observation time is database time; HTTP errors are unavailable, browser deadline is observation timed out, cached evidence is stale. Terminal outbox state reports publication failure independently from receipt evidence.

Local demo credentials authorize one operator principal and all runs in this dedicated stack. A separate random 256-bit demo bearer token is entered at runtime, kept in memory, never VITE_* or operator/replay credentials. Both reads and writes require it. Browser requests additionally require the configured exact Origin and a custom header; no CORS or cookies. Non-browser read-only inspection uses the same credential. No payload/SQL/admin endpoint. This is a local portfolio boundary, not public multi-tenancy.

Limits: 100 retained runs (capacity stop, no eviction), 4 unfinished nonterminal runs, body 1024 bytes, two HTTP requests in flight, global 10 requests/second, 8-second operation deadline, two demo pool connections, 3-second statement/1-second lock timeout. Relay/consumer keep their existing finite budgets, one in-flight delivery each. Fixed tiny payloads; Docker CPU/memory/PID/log budgets. Poll one request at a time every second for 60 seconds, abort on close/unmount. Close stops observation, never the durable run. The token remains only for the mounted experience; the request UUID is retained in same-tab sessionStorage for safe retry after close/reload. Expanded session recovery belongs to 6.3.

Evidence has no TTL and survives normal stop/start. At capacity, stop admitting; never delete receipts while redelivery remains possible. Manual full dedicated-stack retirement requires stopping all demo applications and deleting only this project's broker volume (delivery fence), then its PostgreSQL volume, losing all demo evidence. Export desired evidence first. No per-run DELETE API; no shared resources or original event are included. 6.2 requires an idempotent bounded publication of the identical stored envelope and actual correlated Duplicate handler evidence. A second receipt is not expected. Broker activity plots are deferred; management topology is linked without credentials.

Primary semantics: [PostgreSQL statement snapshots](https://www.postgresql.org/docs/18/transaction-iso.html) and [RabbitMQ independent acknowledgements](https://www.rabbitmq.com/docs/confirms). These references explain the design, not validation of this implementation.

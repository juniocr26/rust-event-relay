# Milestone 4.2 — atomic PostgreSQL inventory persistence

Implemented 2026-10-13 on base `4d3734c79b3d635a91a4e7d415a903b18b43a610`. Both repositories started clean; Library base `281231333240e20a9704e15bb9fbcdaeb5ed151c`. This delivers the local database effect behind 4.1, without RabbitMQ consumption, ACK execution, quarantine publication, producer endpoint or frontend integration. Shared rollout is separate.

## Representation v1

[Adapter](../../../backend/src/infrastructure/postgres/consumer.rs) stores a SMALLINT version (only 1) and BYTEA containing UTF-8 serde JSON serialization of the validated complete EventEnvelope. Included fields: event ID/type, aggregate type/ID, schema version, occurrence instant, correlation/causation IDs and payload. Excludes transport properties, unknown top-level fields discarded by canonical envelope restoration and relay lifecycle/history. No digest or Debug comparison. Serialization is an encoding, not an equality oracle: decode into the checked InventoryEvent and compare its model equality.

JSON object ordering/whitespace are ignored, strings remain exact, arrays retain order, occurrence timestamps compare UTC instants, absent/null optional IDs restore None. Inventory v1 accepts exactly warehouse_id/sku/quantity; quantity must be positive signed i64 integer, rejecting decimal/exponent syntax and out-of-range integers. Installed serde_json arbitrary_precision semantics are retained. BYTEA avoids JSONB numeric normalization, PostgreSQL text NUL restrictions and TIMESTAMPTZ microsecond truncation of the immutable occurrence instant (including nanoseconds). Receipt completion time is database TIMESTAMPTZ, checked by the existing safe decoder for infinity/range.

Stored content is 1..16384 bytes; valid inventory identifiers are 1..128 ASCII bytes with no trimming/case folding. Encode checks the size and decode/equality round trip before acquiring a connection; unsupported input returns Invalid(Unsupported) before mutation. Stored malformed content, unsupported format, wrong ID/effect fields, missing/invalid completion, invalid stock or inconsistent before+quantity=after returns InvalidStoredData, without applying another effect. Arbitrary JSON accepted by the generic envelope is not thereby supported by this inventory adapter. No unsupported representation is silently normalized.

## Schema and trigger rationale

[Additive migration 20261014000000](../../../backend/migrations/20261014000000_add_atomic_consumer.up.sql) creates consumer.stock (warehouse_id,sku PK; nonnegative BIGINT units) and consumer.receipts ((consumer_name,event_id) PK; nonnil UUID; immutable representation, positive quantity, stock_before/stock_after and finite completed_at). C collation gives exact identifier keys. Only the two PK indexes are needed for adapter access; the deferred stock FK permits receipt ownership before absent stock creation. Receipts remain indefinitely. Down drops all consumer state and enables old events to apply again; validate down only in exact isolated databases. Earlier migrations are untouched.

Receipt ownership is inserted with all three completion fields NULL. The CHECK permits this temporary state or a fully coherent receipt, using NUMERIC arithmetic to avoid BIGINT constraint overflow. A regular NOT NULL/CHECK would reject the reservation before stock locking; a separate ownership table would introduce another lifecycle/cleanup invariant. A stored-procedure-only interface could insert a complete receipt later, but would replace the selected Rust transaction protocol. Retain the deferred AFTER INSERT/UPDATE constraint trigger: at enforcement it selects the final row, never trusts the incomplete INSERT NEW snapshot, and requires all completion fields. Immediate guarding forbids identity changes, changes to already completed receipts, DELETE and TRUNCATE. Stock FK prevents deleting linked stock. These cover the adapter's temporary state and receipt retention, including relevant updates/removals.

A complete receipt alone does **not** prove a stock write. The checked effect fields, stock FK and adapter's transaction jointly link the effect; an arbitrary privileged SQL writer can still invent a coherent receipt or alter stock. This is not tamper-proof audit. Owner/superuser/DDL can disable triggers. PUBLIC has no schema/table/function grants. Deployment grants USAGE on schema, SELECT/INSERT/UPDATE(units) on stock, and SELECT/INSERT/UPDATE(stock_before,stock_after,completed_at) on receipts. No DELETE/TRUNCATE/DDL. No role/credential changes or RabbitMQ topology are introduced. Test-only corruption disables the receipt guard exclusively in a test-owned database and restores it.

## Exact transaction: 10 + 5

At explicit READ COMMITTED, insert receipt ownership ON CONFLICT DO NOTHING RETURNING event_id. A unique-index competitor waits for commit/rollback. If it loses, a **separate SELECT statement** gets a new snapshot and restores the winner's completed receipt. A single CTE cannot assume its earlier snapshot sees an uncommitted conflicting tuple. Missing row or unreadable state returns a truthful failure. Equal immutable content returns Duplicate with its original stock_after; changed content returns IdentityConflict. Neither mutates stock. Read paths roll back their transaction; no read-only lookup port is needed because identical reprocessing is already safe.

A winning caller INSERTs missing stock at zero ON CONFLICT DO NOTHING, locks the stock row FOR UPDATE, validates current units and uses domain checked addition. Update stock, then complete the owned receipt, then COMMIT. Lock order is identity first, stock second; each call owns one event/stock key. No stale arithmetic, SKIP LOCKED, broker I/O or automatic transaction retry. Different events on one stock row serialize; different logical consumers have independent identity scopes but share stock and may each increment it. The caller must provision separate broker queues for different logical responsibilities later.

Fixture stock 10 plus event A quantity 5 commits stock 15 and receipt A(stock_after=15). Duplicate A remains 15. Distinct B adds 5 to 20. A later duplicate A still returns 15, while current stock remains 20. Conflicting A changes nothing. Absent stock begins at zero. Overflow rolls back reservation and any absent-stock creation, returning Invalid(Overflow). Any statement failure rolls back both writes; the deferred check can reject COMMIT and roll back the complete transaction.

## Outcomes, deadlines and uncertainty

Applied is returned only after SQLx acknowledges COMMIT. SQLx 0.8.6 source was inspected: Transaction::commit awaits the PostgreSQL transaction manager; Drop queues rollback while open. Drop/cancellation cannot retract a COMMIT already received by the server. Existing ownership::map_commit_error classifies known server rejection as PreCommit and lost/unknown acknowledgement as CommitUncertain. Statement rejections, lock/statement deadlines, deadlock SQLSTATE 40P01 and serialization failures return sanitized PreCommit. Pool/acquire/connect failures return Unavailable; checked decoding returns InvalidStoredData. Typed diagnostic sources are retained behind sanitized Display/Debug, and must be redacted before logging. InvalidStoredData is an explicit new application failure category; recovery never ACKs it. No hidden retry or independent receipt lookup is added.

Pool construction/configuration belongs to the caller: configure finite acquire_timeout, lock_timeout and statement_timeout; wrap overall admission/operation/shutdown in bounded deadlines. Tests use 10s acquisition, 3s locks, 5s statements and bounded observation/proxy waits, plus a 100ms lock-timeout fixture. The adapter does not override session deadlines. No fairness or throughput guarantee is claimed.

CommitUncertain remains uncertain until a later same-identity call restores durable evidence. If the first call committed, identical reprocessing returns the historical Duplicate; if it rolled back, the later call can apply. A negative observation cannot rule out an in-flight commit. An unpolled future does not begin mutation; cancellation while waiting or after writes suppresses the result, without general rollback proof. The fault proxy observes server COMMIT and withholds acknowledgement, proving durable stock/receipt independently in that test. It does not prove power-loss durability or process-kill recovery.

Future delivery policy permits ACK only for Applied/Duplicate; conflict/invalid require confirmed routed quarantine preservation first, and failures/uncertainty/cancellation require paced recovery. No ACK adapter exists in 4.2.

## Revalidation and diagnostics correction — 2026-10-16

The existing 4.2 implementation was already committed at `652bbd21e1cac5dbd4fe587fcf03dcd73a906625`. Reused its schema, representation and protocol; no migration was added or edited. The confirmed gap was source-dropping error mapping: `ProcessingFailure` now wraps the existing sanitized `PersistenceError`, exposes `ProcessingFailureKind` and retains typed SQLx/JSON/model diagnostic sources. Application callers match `error.kind()` rather than a unit error enum; the port still has native Send futures and no SQLx dependency. `Unavailable` distinguishes pre-COMMIT infrastructure failure from `PreCommit` rejection. Every error still requires paced recovery under the future ACK policy. Sources can contain secrets; public formatting excludes source text. A known COMMIT rejection retains its SQLx source; transport loss during COMMIT stays CommitUncertain.

The completeness test now creates the referenced stock first, then asserts SQLSTATE 23514 and the completeness trigger's fixed message. A foreign-key failure alone would not demonstrate this trigger. Statement and deferred rejection tests inspect typed sources; a closed-pool test verifies Unavailable and no mutation. Private decoder tests reject unknown versions and malformed/empty content without weakening constraints.

Actual durable table observations in the existing effect/history test are:

| After acknowledged operation | consumer.stock(local, SKU-1).units | Receipts for inventory.stock.v1 |
| --- | ---: | --- |
| Initial fixture | 10 | none |
| A, quantity 5 | 15 | A: before 10, after 15, completed_at set |
| Identical A | 15 | same A receipt |
| B, quantity 5 | 20 | A: after 15; B: before 15, after 20 |
| A again or conflicting A | 20 | unchanged; duplicate returns 15, conflict returns no effect |

Inside A's transaction only, the reservation has NULL completion fields before stock is locked and incremented. Deferred validation prevents that reservation from committing incomplete. Before COMMIT, statement failure rolls back the effect and receipt; after server COMMIT, loss of acknowledgement or cancellation can hide success. Neither the trigger nor the receipt alone proves arbitrary SQL writers followed the stock protocol. The FK, checked result and transaction provide linkage under the documented restricted-writer assumptions. Relay `processed` still records publication completion, independently of these consumer tables.

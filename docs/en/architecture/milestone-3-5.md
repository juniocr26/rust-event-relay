# Milestone 3.5 — Authorized, idempotent and auditable replay

Implemented 2026-10-13. [ADR 009](../adr/009-authorized-idempotent-replay.md) defines trust/locking/eligibility; [operator API](../operations/replay.md) defines setup, safe request/lookup examples and uncertainty handling.

## Implementation

Driver/HTTP-independent ReplayIntent, ReplayReceipt and focused OutboxReplay Send-future contract; application replay/outcome checks authorization on every path. Concrete HTTP bearer credentials derive actor/permission from trusted bounded configuration. POST mutates; GET observes actor-scoped receipt; existing health remains liveness. No payload/credentials/audit evidence in responses and no frontend changes. Disabled by default; opt-in composition checks replay schema without migrating.

PostgreSQL coordinates global request identity before exact event lock. Explicit intent and prior terminal evidence are durably inserted in new immutable audit table with the single cycle transition. Original envelope/identity/timestamps/lifetime counter survive; new cycle uses current count as baseline, authorized budget, checked revision and post-lock database availability. Repeated intent returns the historical receipt even after worker advancement; changed intent or stale competing event revision conflicts. Invalid/unsupported content, unsafe metadata and exhausted capacity reject without repair. Failure/cancellation semantics reuse existing classification and fault proxies. Detailed capacity/audit-role limits are in ADR 009.

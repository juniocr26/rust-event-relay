# Milestone 2.3 — PostgreSQL delivery ownership operations

Implemented 2026-10-12 from clean `bbc2c1f`. [ADR 007](../adr/007-durable-delivery-ownership.md) remains authoritative; no model, lifecycle or public signature was redesigned. See [executed validation](../testing/validation-results.md#milestone-23--2026-10-12) and the [Portuguese continuity report](../../../Reports/MILESTONE_2_3_HANDOFF.md).

## Implemented scope and contracts

`PostgresOutboxRepository` now implements `OutboxAcquirer`, `OutboxCompleter` and `OutboxReleaser`, alongside the unchanged observation port. SQL/transactions/error mapping live in [postgres/ownership.rs](../../../src/infrastructure/postgres/ownership.rs); checked envelope decoding is shared with the reader in [postgres/mod.rs](../../../src/infrastructure/postgres/mod.rs). Domain/persistence remain independent of SQLx/Lapin; native Send futures and static dispatch are preserved. No dependencies or migration SQL changed. Pool lifecycle and production deadlines remain caller responsibilities.

The actual 2.2 contract acquires **at most one** event, with a single-use request containing a fresh token and positive whole-microsecond duration. It has no caller cutoff or batch limit. `EligibleRead`/`BatchSize` belong only to observation. No batch API was added to satisfy an assumed contract. Release takes only `OwnedEventKey`: it preserves availability and last_error rather than accepting diagnostics or selecting backoff. These are existing decisions, not missing implementations of extra fields.

| Operation | Locked-row predicate at decision time | Committed mutation |
| --- | --- | --- |
| Acquire | pending, availability due, no lease or expired lease, attempts below i32::MAX | Request token, acquired_at, expires_at, attempts + 1; pending unchanged |
| Complete | ID/token match, pending, acquired_at <= time < expires_at | processed, processed_at=time, all three ownership fields NULL |
| Release | Same authority predicate | All three ownership fields NULL; pending, availability, attempts and diagnostic unchanged |

Completion persists the caller's confirmed-publication decision. It neither contacts RabbitMQ nor independently proves acceptance. `processed` does not mean consumer processing. Missing, terminal, unowned, wrong-token, expired and repeated transitions return `OwnershipLost`; they never become presumed success or an infrastructure exception. Event envelope, created_at and unrelated metadata survive transitions. Attempts count acknowledged committed acquisitions, including later-expired acquisitions, not sends; an uncertain commit may also have durably incremented the count.

## Transactions, locking and clocks

Every mutation explicitly chooses Read Committed in a short SQLx transaction. Acquisition first samples `clock_timestamp()` as a **selection cutoff**, then selects the first candidate in availability/created_at/ID order with `LIMIT 1 FOR UPDATE SKIP LOCKED`. The inclusive availability/expiry and strict counter predicates filter candidates. Locked candidates can be skipped; `None` means this invocation acquired nothing and cannot establish empty backlog or fair ordering. A lease becoming due after the cutoff may wait for a later invocation.

After obtaining the row lock, acquisition restores the selected envelope through checked decoding and samples a second authoritative database instant. It rechecks state, availability, expiry and counter against the locked row; that instant is the decision point for eligibility and both lease timestamps. Duration addition and counter increment are checked before mutation. Exhausted rows remain pending and observable, excluded from acquisition with no wrapping, saturation or automatic terminal policy. Invalid selected stored data fails the whole single-row invocation before mutation; it is never silently skipped for another candidate. Persistent malformed candidates can impede progress.

Completion/release lock by event ID alone with `FOR UPDATE`, allowing a lock wait. Only afterward do they sample database time in a separate statement and issue a conditional UPDATE using that same instant. The lock remains held through mutation and commit, so another acquirer cannot replace authority in between. At equality with expires_at the predicate rejects; a clock before acquired_at also rejects. `now()`/transaction-start time cannot authorize these transitions after waiting. Clock monotonicity is not guaranteed. [PostgreSQL time functions](https://www.postgresql.org/docs/18/functions-datetime.html), [row locking/SKIP LOCKED](https://www.postgresql.org/docs/18/sql-select.html) and [Read Committed](https://www.postgresql.org/docs/18/transaction-iso.html) describe the relevant server behavior.

The sampled post-lock instant, rather than commit/response time, decides validity. Ownership becomes durable at commit. Commit latency and returning the response consume lease time: acknowledged acquisition can return an already expired lease. No lock, transaction or checked-out connection escapes these methods for external publication. Short transactions avoid remote publication waits; they do not impose a production timeout or prove low latency under DDL/contention. No performance benchmark, fairness or planner-cost claim is made.

## Errors, commit uncertainty and cancellation

Before COMMIT is attempted, driver failures use existing Unavailable/InvalidStoredData/OperationFailed mapping. An open SQLx transaction queues rollback when dropped; eventual cleanup is not immediate rollback acknowledgement. Known errors do not expose a successful claim. There are no hidden retries.

At COMMIT, an ordinary server-reported rejection uses the existing mapping: a deferred constraint rejection, for example, is OperationFailed and rolls back. Transport/protocol/worker errors, missing server codes, SQLSTATE class 08, 40003 and shutdown/unready 57P01/02/03 conservatively use CommitUncertain. This classification is specific to the commit boundary; it does not relabel every query error. A server code absent from an error cannot prove rollback. Typed sources remain available; public formatting stays sanitized and methods emit no logs. See [PostgreSQL error codes](https://www.postgresql.org/docs/18/errcodes-appendix.html).

Uncertain acquisition returns an error, never ordinary owned data. Do not publish blindly or retry the old request token; inspect durable lease state operationally or allow expiry and acquire with a new request. After uncertain completion, processed may already be durable: neither assumed failure nor blind republishing is justified. Uncertain release likewise does not prove retained ownership. Reconciliation belongs to the caller/operator, with orchestration deferred to 2.4; no new read/reconciliation port is invented here.

Dropping a future before COMMIT does not establish immediate rollback. During COMMIT, cancellation may suppress the result while the database commits; a cancelled future cannot necessarily return CommitUncertain. SQLx's queued rollback cannot undo an already committed transaction. The cancellation integration test covers a blocked pre-mutation transition only, not cancellation during COMMIT or abrupt process death. Database tokens guard transitions, **not RabbitMQ publication**: stale workers can still send, and broker acceptance followed by failed/unknown completion can duplicate during recovery.

## Evidence and remaining work

[postgres_ownership.rs](../../../tests/postgres_ownership.rs) contains 12 isolated real-PostgreSQL cases: eligibility/single-row bounds, token/timestamps/count, live-lease exclusion and unchanged reader observation, successful/repeated/wrong/missing/terminal transitions, expiry/reacquisition/stale tokens, concurrent disjoint acquisitions, locked-row skipping, malformed data/overflow rollback, maximum counter, before-acquired_at rejection, expired return, immediate and deferred server rejection, and cancellation during lock wait.

The lock-wait case observes pg_stat_activity's Lock state, verifies transaction start precedes expiry, waits for the database clock to reach expiry, then unlocks. It tests both completion and release. Activity snapshots are explicitly refreshed; bounded polling is coordination rather than a fixed sleep assumption. Exact expiration equality is demonstrated by the existing deterministic delivery model tests; integration demonstrates expiry around real waits, not controlled exact equality. No live database clock was modified.

A controlled test-owned PostgreSQL connection proxy forwards protocol frames but discards the server's CommandComplete COMMIT response. For acquisition, completion and release the adapter returns CommitUncertain while an independent connection observes committed state. Uncertain acquisition returns no ordinary owned event; its durable lease excludes immediate reacquisition, then an expired fixture recovers with a new token/count. Repeated completion/release after the uncertain committed transition return OwnershipLost. This experiment injects response loss **after** observed server completion: it proves a committed uncertain outcome is possible, not that arbitrary uncertainty always means commit or rollback. The proxy uses only an isolated database/connection and explicit non-TLS test connection; it does not restart services or intercept shared application traffic.

Cancellation during commit, process/network loss before observed server completion, acquisition after a DDL wait/clock reversal, every isolation/write schedule, production performance and power-loss durability remain unverified. The before-acquired_at fixture tests the lower authority bound, not actual wall-clock reversal.

Tests apply ownership migration only in exact generated fixture databases and verify cleanup. Read-only development metadata on 2026-10-12 shows the two original migrations installed and no ownership_token column; ownership migration stays pending there. HTTP/runtime/services/data were preserved. CI now includes the ownership suite; remote CI is not asserted.

**Next: 2.4 delivery use-case orchestration** — one acquisition → publication through EventPublisher → completion only on confirmed acceptance, otherwise release/reconciliation according to explicit outcome handling. Reuse these ports, stable event ID and tested publisher error categories; first decide how to surface ownership loss, uncertain persistence and cancellation without blind retry. Polling, Supervisor worker registration/reconnection, retry/backoff/DLQ policy, producers, consumer idempotency and end-to-end crash/recovery belong to later scope.

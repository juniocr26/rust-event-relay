# Milestone 3.1 — Durable failure policy and recovery contracts

Decision date: 2026-10-12. Status: policy accepted for implementation in 3.2–3.6. Only pure calculations exist in 3.1; no durable retry, isolation or replay transition is implemented. This extends the completed Milestone 2 scope without treating its deferred features as defects.

## Baseline and invariants

Inspected: [Milestone 2 acceptance](../operations/milestone-2-review.md), [2.3](milestone-2-3.md), [2.4](milestone-2-4.md), [2.5](milestone-2-5.md), [2.6](milestone-2-6.md), [ADR 007](../adr/007-durable-delivery-ownership.md), delivery domain, persistence contracts/errors, PostgreSQL ownership, publisher/adapter, use case/worker, migrations, integration/recovery tests and frontend scenario definitions. Historical test evidence remains historical; current executions are in [validation results](../testing/validation-results.md).

Event ID and the entire original envelope survive acquisitions and replay. Fresh tokens identify acquisitions, never events. Leased rows remain pending. attempt_count counts committed acquisitions, including crashes before publication; acquisition does not establish that sending began. Completion requires confirmed acceptance plus valid database authority. Tokens fence database transitions, never RabbitMQ sends. CommitUncertain proves neither commit nor rollback. Failed/uncertain completion permits no blind republication or compensating release. Current release clears ownership and preserves available_at, last_error and attempt_count. Worker pacing is volatile, not durable scheduling. No existing port provides generic reconciliation.

## Authority and recovery notation

**O**: lock the exact ID, then sample PostgreSQL clock_timestamp(); require pending, expected token, acquired_at <= now < expires_at, expected cycle/revision. Future schedule/terminal operations atomically update state, diagnostics, revision and clear ownership; no counter increment. Application clocks cannot authorize them.

**M**: maintenance transaction locks the exact raw row without constructing OwnedOutboxEvent; rechecks pending, expected revision/raw snapshot and absent or expired lease with post-lock database time. It may isolate invalid or exhausted rows without acquisition or sending. It must not overwrite a live owner. Migration must supply a revision incremented on every relevant mutation; external writers require the same contract or a full expected-snapshot comparison.

**R**: independent exact-ID durable observation can establish present status/token/cycle, not broker nonacceptance. Acquiring only after due time/lease expiry with a fresh token is the existing recovery fallback and can duplicate. Broker queue inspection/absence is not proof that a consumer never processed the event. Future reconciliation needs a separately specified evidence source and port.

## Scheduling contract

Default qualifying outcomes: definitive Unroutable/Rejected and unresolved event-specific serialization, while budget remains. Verified permanent defects isolate instead. Before-send infrastructure unavailability and global encoder/topology defects require infrastructure recovery, not a per-event schedule. This prevents representing system outages as proof of invalid content, but acquisitions already committed still consume budget. Connection usability can race acquisition; budget consumption is deliberately conservative.

Default maximum: **10 acquisitions per cycle**, inclusive: counts 0–9 permit the next acquisition; count 10 permits completion of the already acquired final attempt, but no eleventh acquisition or retry scheduling. A definitive failure at 10 terminalizes; uncertainty retains its lease until maintenance can safely terminalize after expiry. This can preserve a terminal event already accepted by the broker: terminal means relay policy stopped, never proven non-delivery. Crash on the final acquisition before send also consumes the final slot.

Default backoff: base **1,000,000 µs**, cap **300,000,000 µs**. For one-based cycle acquisition n, ceiling=min(cap,base*2^(n-1)); calculate with bounded checked doubling, stopping at cap. Equal jitter selects an unbiased whole-microsecond delay uniformly in [ceil(ceiling/2), ceiling]. Positive floor avoids a zero-delay loop. Valid settings: 0 < base <= cap <= 86,400,000,000 µs; budget 1..i32::MAX. No retry hints in this design; a future hint needs a separate bounded contract and cannot bypass cap/budget.

Application supplies a validated selected delay with explicit randomness; repository samples the authoritative PostgreSQL UTC clock after row lock, checks addition, and persists available_at=now+delay at microsecond precision in the same ownership-protected transaction as sanitized diagnostic/revision and lease clearing. A pure calculation with an explicit clock models this formula; no adapter retries or trusts an application timestamp for authority. Reject sub-microsecond inputs, arithmetic/date overflow and timestamps not representable by both Chrono and PostgreSQL; never round silently. Expired ownership means OwnershipLost, leaving state unchanged. Invalid delay/configuration fails before mutation. Only committed available_at/diagnostics/counters/cycle survive restart; randomness is sampled once per proposed transition, and an uncertain commit is observed rather than blindly recomputed. Worker pacing remains infrastructure/admission protection, additive to durable eligibility; it cannot shorten persisted due time.

## Budgets and future schema

Compared options: acquisition budget is observable atomically with current claims, but charges crashes and before-send outages. A publication budget better describes sends but cannot durably count external calls/acceptance atomically with PostgreSQL; a new intent/ack protocol would still expose uncertainty. A per-replay-cycle budget permits controlled recovery while retaining lifetime history. Choose acquisition budget with a persisted cycle baseline, not a second publication counter or reset lifetime count.

3.2 proposed additive versioned migration: cycle ID, cycle baseline, cycle maximum and revision; structured diagnostic code/time and bounded sanitized metadata; terminal timestamp/reason and isolation evidence snapshot as needed. Existing rows receive an initial cycle with baseline **0**, maximum 10 and revision 0: historical acquisitions count, rows already at/above 10 need maintenance isolation without another send. Do not initialize baseline to current count and silently grant a new budget. Terminal existing rows remain terminal; processed rows stay processed. Preserve original event fields, attempt_count, existing diagnostic history and available_at until an authorized transition. Explicit rollout audit must count existing exhausted rows before activation; no shared migration is applied in 3.1. Persist cycle maximum for stable behavior across restart/config changes. Replay baseline becomes current lifetime count, cycle maximum is explicitly audited; available storage capacity remains a hard independent bound.

Acquisition must atomically check due time, pending, absent/expired lease, cycle allowance and storage bound before increment. Scheduling must validate remaining budget under O; terminalization must not increment attempts. Exhausted rows excluded from acquisition need M processing rather than remaining invisible forever. Port input/output semantics and timestamp representability require implementation and concurrency/fault tests in 3.2.

## Poison isolation and diagnostics

Choose existing **dead_letter** terminal outbox state plus structured evidence/audit, instead of moving/deleting events into a separate quarantine table. It preserves identity and avoids duplicate lifecycle authorities. A separate quarantine record would aid access separation/raw evidence retention but introduces atomic-copy and replay consistency costs; an audit/evidence side record may supplement the retained row if required. Broker DLQ handles broker/consumer routing policies and cannot isolate a row that never publishes; application quarantine is a database lifecycle decision.

Permanent evidence includes reproducible envelope validation failure or a documented event-specific encoding incompatibility. Error names, outage duration or topology failure alone are insufficient. Budget exhaustion is an operational terminal reason distinct from poison. Use static codes invalid_stored_envelope, serialization_permanent, acquisition_budget_exhausted, storage_counter_exhausted; bounded metadata includes validator/policy version, phase and evidence reference, never payload, driver text, credentials or connection strings. Proposed metadata bound: 2 KiB UTF-8 serialized JSON, allowlisted keys; reject excess rather than truncate ambiguously. Original raw row is protected evidence, not public diagnostic text.

A valid owned row uses O; an unrestorable envelope requires M with identity/raw snapshot and revision independently of OwnedOutboxEvent. Current acquisition error lacks selected ID: 3.4 needs a bounded raw-row maintenance scan that validates and isolates each offending row in its own short transaction. It must bypass normal valid-envelope acquisition and scan invalid/exhausted due rows without letting one repeatedly block independent valid work. SKIP LOCKED can reduce contention but does not prove fairness. Invalid ownership/identity shapes require privileged audited repair under a maintenance window; never invent a valid envelope, delete evidence or clear a live owner's claim. If the envelope cannot be restored, retain it terminal and refuse replay until a separately authorized, auditable repair makes it valid; ordinary replay cannot mutate content.

Retention has no automatic deletion in Milestone 3. Restrict raw events/evidence to operator access; expose sanitized reasons only. Production retention duration, privacy/legal deletion procedure and operator authorization integration remain deployment prerequisites. Terminal isolation has processed_at NULL and is never counted as successful delivery.

## Replay contract (3.5 planned)

Only application dead_letter rows with a restorable unchanged envelope are eligible; pending/processed and live-owned rows are rejected. Explicit authenticated operator intent supplies source revision, reason, request ID and expected cycle. Lock/recheck expected state/revision and no owner, then atomically audit actor, reason, requested/applied database timestamps, source/new cycle IDs, prior baseline/count/budget and selected new budget. Preserve event ID, envelope and lifetime attempt_count; new cycle baseline=current count, fresh cycle ID, available_at=post-lock database time, clear terminal current-state metadata while preserving audit history. Reject storage-exhausted rows; capacity widening requires its own design. No replay endpoint, UI or tool is added now.

Unique request identity plus durable audit supports returning the same committed result for an identical repeated request; mismatched reuse is a conflict. Competing requests against the same revision allow one transition; the other conflicts. Replay CommitUncertain requires lookup by request ID and state/cycle observation, never a blind fresh request. 3.5 must implement this observation capability; current ports cannot do it. Repair/replay are distinct operator intents. Consumer deduplication by original ID may intentionally cause **no additional business effect** if that ID was previously committed atomically with the consumer's business transaction. Replay is renewed delivery intent, not guaranteed renewed effect or exactly-once processing.

## Frontend and evidence boundary

Existing Vue components and scenario playback remain unchanged and disconnected from infrastructure. Once implemented, future illustrative scenarios may show persisted retry due time versus worker wait, final acquisition/budget exhaustion, preserved quarantine, explicit replay/new cycle with original ID and consumer dedup no-op. Actions, status and progress must remain distinguishable; button count is a contextual UX choice. A simulation cannot verify a backend capability.

Pure [policy calculations](../../../backend/src/application/retry_policy.rs) and [tests](../../../backend/tests/retry_policy.rs) validate budget/history boundaries, capped exponential growth, equal-jitter bounds, precision and overflow only. They do not validate durable scheduling, SQL contention, quarantine, replay or recovery. No dependencies, migrations, adapter/use-case/worker behavior or frontend were changed in 3.1.


Historical counts predating ownership acquisitions cannot be reconstructed; baseline zero conservatively preserves their budget impact. Proposed schedule/terminal ports perform one transaction and return Applied or OwnershipLost for O predicate mismatch, retaining existing PersistenceError categories including CommitUncertain. Acknowledged repeated transitions with the old token/revision are rejected, not treated as idempotent success. M revision conflicts leave the row unchanged. Revision/audit-counter arithmetic must be checked; exhaustion refuses the transition without wrapping.

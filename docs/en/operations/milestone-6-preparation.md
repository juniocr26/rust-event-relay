## Architectural comparability

Comparable purpose: publish committed outbox events while recovering interrupted progress. Different mechanisms: R1 decodes INSERTs from `pgoutput` logical replication, buffers rows until COMMIT, then sends events and an observed-progress marker. Its checkpoint counts outstanding events per commit LSN and cannot advance past an unconfirmed event or unobserved transaction boundary. Feedback advances the existing replication slot; it never recreates a missing slot automatically. This is CDC for a configured outbox, not arbitrary-table CDC or polling.

C1 acquires eligible pending rows with short READ COMMITTED transactions, `FOR UPDATE SKIP LOCKED`, a committed token and database-clock lease. After routed publisher confirmation, completion rechecks current token/state/lease under the row lock. A lease expiry allows recovery; an old token cannot complete a new owner's transition. It cannot prevent the expired worker from publishing externally. Selection order is not a global or per-aggregate commit-order guarantee.

| Responsibility | Reference | Current |
| --- | --- | --- |
| Durable source | Committed outbox INSERT plus retained WAL/valid slot | Committed outbox row and durable retry/ownership state |
| Acquisition/position | One active receiver per slot; stream commit order | Row ownership across workers; one operation per process |
| Destination acceptance | Per-entry sink response; adapter-specific semantics | Mandatory routing plus RabbitMQ publisher confirm |
| Source progress | Safe LSN after publication or durable dead-letter storage | Ownership-protected processed/terminal row transition |
| Interrupted progress | Resume slot; replay unacknowledged range | Lease expiry/reacquisition; original identity republished |
| Duplicates | Stable source:id; FIFO window where applicable; consumer responsibility | Stable UUID; receipt plus local stock effect in one SQL transaction |

These designs are not fully equivalent. At-least-once depends on retained source state, working recovery, eventual destination availability and appropriate durable configuration; terminal preservation is not successful business delivery. RabbitMQ confirm, SQL relay completion, consumer effect and consumer ACK-send are separate facts. ACK-send success does not prove broker receipt. Neither design supplies exactly-once transport, universal delivery or atomicity with arbitrary external effects.

## Smallest proposed live demonstration architecture

Use a **dedicated local demo stack**, with one small demo HTTP service/BFF in the same private namespace as its own relay, consumer, PostgreSQL and RabbitMQ. Reuse current Rust ports/adapters and Vue components; avoid per-run container orchestration in the browser or a general administration service. Separate DB and broker/vhost/credentials from the preserved shared demonstration. Per-run warehouse/SKU and event IDs prevent interference inside the demo stack; a fixed named consumer retains deduplication responsibility. Future fault slices need a separately owned disposable stack, not faults against this successful-delivery stack. This is proposed future provisioning, none performed here.

Proposed contracts, absent today:

- `POST /demo/runs`, authenticated session plus idempotency key, allowlisted scenario (`normal` initially), no raw event/SQL/shell input. Return 202 + run_id, event_id, status URL, accepted_at and expires_at. 202 establishes admission only. Persist principal + key + normalized intent; identical repetition returns same run; divergent reuse gives 409. On response/commit uncertainty inspect using the same key; never create another event automatically.
- Minimal producer transaction: lock/admit the durable demo request, insert immutable `demo.goods_receipts` business fact (run, warehouse, SKU, quantity), outbox `inventory.units_received` v1 envelope and run/event mapping, then COMMIT together. A failure before COMMIT leaves neither fact nor event; an ambiguous COMMIT requires lookup. Consumer stock is a separate downstream effect, not the producer fact. Seed stock 10 only for the new owned key; fixed quantity 5. Put run correlation in supported envelope correlation_id and mapping, not an extra payload key (C4 accepts exactly warehouse_id, sku, quantity).
- `GET /demo/runs/{run_id}` and a principal-scoped lookup by request key return bounded snapshots: run lifecycle and revision; producer fact/outbox state; receipt with stock_before/after/completed_at; separately observed current stock; per-step source/time; unknown/unavailable/stale/expired states. Authorize reads too; UUID is not authorization. Read receipt/stock in a consistent read-only transaction where coherence is claimed. Status absence during DB failure is unavailable, never “no effect”.
- Store a small fixed-vocabulary evidence trail for each owned run/action. Instrument actual publisher/handler outcomes, including Applied/Duplicate and ACK-send separately; existing process metrics lack run labels/history. Evidence may lag a durable effect after a crash; SQL receipt remains the effect authority. Do not assert exact arrival/acceptance counts from receipt count, outbox attempts or aggregate metric deltas. Consumer ACK received by broker remains unverified. Mark “not observed” rather than manufacture a complete timeline.
- Later `POST /demo/runs/{id}/duplicate` accepts an action idempotency key and publishes only the immutable stored envelope with original message_id, once per admitted action. A crash between publish and recording confirmation can duplicate again: report uncertainty; do not promise exactly two transport deliveries. Record a correlated observed Duplicate result before claiming the demonstration succeeded. SQL replay of a processed event is not this operation.
- `GET /demo/observations` exposes allowlisted bounded observations from the demo role exporters with role, observed_at, age and source/error. The BFF accesses loopback exporters in their namespace, not new public ports. Process restarts reset counters. These observations are separate from run completion and must not scan backlog on scrape.

Initial numeric budgets are **proposed defaults requiring implementation validation**: one active run globally, one per session; reject excess immediately with 429, no waiting task queue; at most two publications per selected duplicate run; body ≤4 KiB before parsing; fixed template/identifiers ≤128 ASCII bytes, serialized consumer receipt representation ≤16 KiB. Max 32 evidence entries and ≤32 KiB response/run; fixed timeouts for dependencies; BFF admission capped at four active requests with a 2s observation budget and immediate overload rejection; one outstanding browser poll per modal, 1s while active, at most 60 polls/60s per observation session, stop on terminal/expired and when hidden/closed; manual resume by run ID. A timeout ends observation, not durable execution. Streaming/SSE is unnecessary for these finite runs.

Use an explicit local operator login to mint a 15-minute server-side session with demo-only scope, HttpOnly SameSite cookie, same-origin requests, CSRF token and Origin validation for mutations. Validate Host/Origin; do not rely on loopback binding alone. Keep current operator bearer credentials server-side and outside this demo contract; no VITE_* secrets, arbitrary broker credentials, process IDs, SQL or shell capabilities. Duplicate action, creation and reads require ownership authorization. Return sanitized typed errors with retryability/uncertainty and no diagnostic secrets.

Proposed retention: at most 100 retained runs; evidence/read access expires after 24h; refuse admission if retention/storage budget is exhausted. Expiration is not cancellation and does not release a correctness obligation. Persist run ID/request key for reload; after reauthentication reattach to the owned run. Closing modal/unmount stops polling only. Show actual backend timestamps separately from slower explanatory playback; no fabricated intermediate success or reordered causal claim. API unavailable, stale sample, observation timeout, pending and commit_uncertain must remain visible and distinguishable.

Cleanup must use a durable exact ownership manifest of run IDs, event IDs, business facts, stock keys and action/request records. Never wildcard-delete, purge a shared queue or delete a dedupe receipt while redelivery remains possible. Normal terminal rows may be cleaned only after the selected retention window and a verified demo topology lifecycle fence: retire/close owned admissions and workers, remove the exact dedicated broker resources to eliminate retained source deliveries, then remove the exact owned SQL records; otherwise defer cleanup and reject new admissions at capacity. The protected original event/receipt/key is excluded by construction. Abrupt restart reconciles manifests before admission; incomplete runs remain inspectable. Fault runs have their own manifest and bounded worker deadlines. A local topology rotation is simpler than proving individual message disappearance. Public/production cleanup and multi-tenant hosting are outside this proposal.

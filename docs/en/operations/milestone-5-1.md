### Payload safety and progress

Do not conflate broker acceptance, client buffering, application validation and quarantine capacity. A valid existing large outbox row is **not terminalized because of a new local size preference**: no local outbox cap was introduced. The relay may publish a body the consumer cannot preserve. Broker rejections still follow the existing contextual retry policy; arbitrary serialization errors do not create permanent evidence.

A body >1 MiB, or an invalid/conflicting message whose complete original properties cannot fit the preservation protocol, causes `preservation_blocked`: no source ACK, no truncated quarantine copy, close the session and stop cleanly (exit 0 under current Supervisor policy). Closing recovers buffered unacknowledged messages. This prevents an infinite reconnect/redelivery loop but **halts progress for this consumer**; other consumers can still encounter the same message. Inspect broker/database state without consuming shared messages, preserve exact original bytes/properties using an explicitly designed recovery path, then decide policy before a named restart. Simply restarting cannot resolve the unsupported size. There is no automated large-object quarantine/replay workflow. Future work must coordinate producer admission, broker limits, streaming/spooling, receipt representation and preservation capacity; do not add a post-receipt check and claim pre-receipt memory safety.

Checked conversion of publisher byte length to AMQP u64 now precedes the installed client's cast. Duration configuration is finite and validated; consumer prefetch/pool narrowing is checked. Existing lease conversion and PostgreSQL LIMIT conversion remain checked. Metric elapsed microseconds saturate at u64 max rather than wrapping.

## Observability contract

Registry ownership: one fresh `Metrics` instance in each binary composition; no global registry and no IPC aggregation. Application observation enums/RAII guards have no metric-library/domain coupling. Ports default to `HTTP_METRICS_ADDR=127.0.0.1:9100`, `RELAY_METRICS_ADDR=127.0.0.1:9101`, `CONSUMER_METRICS_ADDR=127.0.0.1:9102`. All must parse as loopback IP socket addresses with ports 1..65535, mutually distinct and distinct from HTTP's port. No disable/public-bind knob; unused processes own no listener. Exporter bind failure fails startup before worker admission. OS bind handles collisions with unrelated listeners. At runtime an accept failure logs and stops that exporter; it does not change delivery correctness. Exporter shutdown aborts/reaps client tasks; dropping it also aborts the task tree. All exits release observations without compensating business actions.

Compose injects the three addresses and deliberately publishes **none** of these ports. Inspect inside app. Loopback in the app network namespace means host `curl localhost:9101` will not reach it. A future scraper needs an explicitly reviewed namespace/exposure design; do not change to a public address. No Prometheus/Grafana dependency or container was added. Existing tracing and Axum/Tokio dependencies are reused; Tokio `io-util` is explicitly enabled for the bounded exporter.

| Metric | Type / units | Labels / meaning |
| --- | --- | --- |
| `relay_observations_total` | counter, observations | `process`, `operation`, `outcome`; typed phase outcomes below. Series appears after its first observation; absence before then means no observed event for that process lifetime, not an unknown durable total. |

Closed `process` values: `http`, `relay`, `consumer`. Closed `operation` vocabulary and emitted meanings:

| Operation | Outcomes / semantic boundary |
| --- | --- |
| `acquisition` | `acquired` after acknowledged owned result; `empty`; `unavailable`, `invalid`, `failed`, `commit_uncertain`; never inferred acquisition after uncertain commit. |
| `publication` | `confirmed` only publisher Ok (mandatory routed confirm); `unavailable` includes saturated admission; `serialization`, `rejected`, `unroutable`, `uncertain`. |
| `completion`, `release` | `applied`, `ownership_lost`, persistence error categories; completion `applied` requires acknowledged DB result. Confirmed publication is counted **before** awaiting completion. |
| `schedule`, `terminal` | `applied` only acknowledged durable retry/terminal preservation, `conflict` or persistence error categories. Terminal is SQL preservation, distinct from broker quarantine. |
| `maintenance` | `observed`, `end`, isolation `applied`/`conflict`, persistence errors; no queue size inference. |
| `processing` | acknowledged `applied`, `duplicate`, `identity_conflict`, `invalid`; failures `failed` (precommit), `unavailable`, `invalid` stored data, `commit_uncertain`. Local decode rejection also emits `invalid`, without a processor call. |
| `quarantine` | `confirmed` only after preservation publisher Ok; publication errors as above; `blocked` when exact protocol preservation is impossible. Counted before source ACK. |
| `ack_send` | `completed` means the installed client's ACK call returned true, **not proof the broker received it**; `uncertain` on error/false/timeout. |
| `connect`, `close` | `completed` for observed successful lifecycle operation; typed transport error categories (connect normally `unavailable`). Includes initial connection and reconnections; no reconnection reconciles earlier acceptance. |
| `delivery` | `completed` means handler/use-case future returned, including a failed business result; consult phase counters. It is not successful delivery. |
| `http`, `replay` | response `completed` for 2xx / `rejected` otherwise; replay `saturated` before body read, `deadline` on 10 s expiry. Replay HTTP completion is not a new authoritative business total or an audit receipt. |
| `shutdown` | composition cleanup `completed` or `deadline`; no guarantee of a final scrape after listener closes. Logs remain necessary for process exit diagnosis. |

Any observed timed future can emit `cancelled` on drop; this releases its gauge, does not prove rollback and never counts success. The finite outcome enum also reserves `reenabled` and `denied`; no current code emits them. No labels contain IDs, consumer name, queues, warehouse/SKU, payloads, arbitrary errors or credentials. Registry allocates fixed arrays (400 possible counter pairs per process), 16 histograms and gauges; rendering only observed counters does not create dynamic label registration. Unrelated zero-valued operation histograms are harmless, not durable-state observations. Each histogram is copied under a short local mutex so its buckets/count/sum are coherent; formatting occurs after releasing the lock. Other atomic fields are individually observed, **not an atomic snapshot across phases**. Counters/sums saturate instead of wrapping at u64 max; histogram sums use microsecond precision exported in seconds.

All observations reset on restart. Aggregate by externally assigned scrape job/instance plus `process`; sum rates across replicas only for like phases. Never use the values as lifetime business totals, replace receipts/audit with counters, or subtract publication minus processing and call it backlog. A crash can occur between durable effect and observation. Local instrumentation performs no external I/O; scraping failure does not block delivery.

Example: broker confirms event E; DB completion returns CommitUncertain. Publication confirmed increases by 1, completion commit_uncertain by 1, completion applied stays unchanged. Another example: processing returns Duplicate, ACK send completes: duplicate +1 and ack_send completed +1, applied unchanged. Neither example proves broker receipt of that ACK.

## Safe local inspection and rollout

```sh
# Read-only; preserve the observed named consumer state.
docker compose exec -T app supervisorctl status
# After an explicitly selected binary rollout, inspect process-local metrics inside app:
docker compose exec -T app python3 -c 'import urllib.request; print(urllib.request.urlopen("http://127.0.0.1:9101/metrics", timeout=3).read().decode())'
# Substitute 9100 (HTTP) or 9102 (consumer). A stopped consumer has no exporter.
docker compose config --quiet
```

Do not use `start all`, `restart all`, purge, `basic.get`, shared fixture publication, load generators or shared migrations for inspection. The running binaries were not restarted to deploy this change. Building replaces files on disk, not loaded process images; the next named restart may load new code. Before rollout, capture named states and intended source admission; review the three free ports/environment, build all binaries, install/recreate app configuration only under an explicitly coordinated rollout, and restore the captured **intentional** consumer state. Existing consumer autostart=true means a manager/container recreation can resume it; do not recreate casually to install environment. A process-only restart can use defaults without new injected variables, but still requires deliberate rollout. No schema migration is required. `/health` remains the same liveness response, independent of database/broker readiness.

Runtime observation in this implementation session: HTTP/relay/consumer were RUNNING at first read (consumer PID 11, HTTP 12, relay 13). This overrides neither the earlier manual-stop report nor user intent; no control command changed them. Six successful shared migrations were read; retained event `481fb751-81d5-46b7-aea2-eed344084725` is processed with one acquisition, stock=15, receipt before=10/quantity=5/after=15/completed. No demo republish was performed. Shared credentials, volumes, replay configuration and topology were not modified. Validation uses new disposable databases and UUID topology on existing services, not shared load tests.
